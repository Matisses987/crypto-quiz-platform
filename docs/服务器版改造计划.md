### 4.2 为什么 `user_stores.doc` 直接存 CQP 的 store

上游 store 形状是 `{meta, records, wrongbook, overrides, sessions, imports}`（见 `src/core/store.mjs` 的 `sr_emptyStore()`）。**原样存 JSON 的好处：**

- 服务端可以直接 `CQP.masteryOverall(store)`、`CQP.teamStats({records, questions})`、`CQP.exportPayload({store})`，不需要任何 schema 翻译层
- 客户端 `S.store` 完全不变 → `renderHome` / `renderWrongbook` / `renderStats` / `renderMock` 等 2000 行渲染代码逐行可用
- 导出文件的格式（`cqp-export` v1.0.0）与上游完全兼容，老用户的本地数据/历史导出文件可以原样导入
- `question_state` 之类的拆表方案会让错题本状态机（`confidentStreak` / `attemptsSinceAdd` / `removedReason`）无处安放，反而制造翻译 bug

代价是并发粒度粗（整文档乐观锁）——对「个人学习记录」这种单写者场景完全够用，冲突时用 §4.3 的合并而非拒绝。

### 4.3 同步协议（乐观锁 + 服务端合并）

```
GET  /api/store            → { rev, store, serverTime }
PUT  /api/store            → body { baseRev, store } → { rev, store, merged:bool, added:{records,wrongbook} }
```

服务端逻辑：

1. `baseRev === 当前 rev` → 直接落地，`rev++`，`merged:false`
2. `baseRev !== 当前 rev` → **不报错**，走合并后落地，`rev++`，返回 `merged:true`

**实测发现（关键）：`CQP.mergeImport()` 只合并 records / overrides / mockSessions，完全不碰 wrongbook。** `src/core/ioport.mjs:337` 只有一行 `if (!io_isPlainObject(next.wrongbook)) next.wrongbook = {};`，之后全程没有再读它。所以合并必须分两步：

**步骤 A —— 用现成的 `CQP.mergeImport` 处理 records / overrides / sessions**

它要求 `payload.kind === "cqp-export"`（`ioport.mjs:331`），所以把 `body.store` 的这几段包成合法 payload：

```js
const payload = {
  kind: "cqp-export",              // cn_EXPORT_KIND
  schemaVersion: "1.0.0",          // cn_EXPORT_SCHEMA_VERSION
  appVersion: CQP.VERSION,
  bankVersion: currentBank.bankVersion,
  exportedAt: nowISO,
  exportedBy: { nickname: store.meta.nickname, deviceId: store.meta.deviceId || "d-00000000" },
  range: { scope: "all", from: null, to: null },
  counts: { records: 0, sessions: 0, overrides: 0 },
  records: body.store.records,
  mockSessions: body.store.sessions,
  overrides: body.store.overrides,
};
const { store, report } = CQP.mergeImport({ store: currentDoc, payload, questions: currentBank.questions, bankVersion: currentBank.bankVersion });
```

现成保障（实测于 `ioport.mjs:367–456`）：

- records 按 `nickname + "\u0001" + qid + "\u0001" + ts` 三元组去重（`report.duplicates` 计数）
- 顺手把 `localDate` 按 `ts` 重算并修正不一致（`report.repaired`）——正是多设备跨时区场景需要的
- 未知 qid 进 `report.unknownQids` 并跳过（题库换版时不污染）
- `bankVersion` 不一致进 `report.versionMismatch`（只报告不阻断）
- overrides 按 `updatedAt` LWW，相同则 `updatedBy` 字典序大者胜
- sessions 按 `sessionId` 去重，已存在不覆盖

**唯一需要补的洞**：`mergeImport` 对 `store.imports` 只做 `next.imports.push({...})`（`ioport.mjs:476`），没有按 `fileName + importedAt` 去重。多设备交替提交时同一个导入批次会重复追加。`server/store-doc.js` 在调完 `mergeImport` 后补一次去重：按 `fileName` + `importedAt` 建 Set 过滤（`imports` 仅用于统计页展示「导入了几个队友文件」，重复项会让这个数字虚高）。

**步骤 B —— wrongbook 自己写 `mergeWrongbook(a, b)`（新增 `server/store-doc.js`）**

上游没有这个原语，必须新写。规则（与 `wrongbookApply` 的状态语义对齐）：

```js
function mergeWrongbook(kind, a, b, nowISO) {
  const out = { ...a };
  for (const qid of Object.keys(b)) {
    const x = a[qid];
    const y = b[qid];
    if (!x) { out[qid] = y; continue; }
    if (!y) continue;
    // 谁最后一次「动过」这条记录，谁的状态生效
    const tx = lastTouchOf(x);   // max(lastWrongAt, addedAt, removedAt) 里非 null 的最大值
    const ty = lastTouchOf(y);
    if (ty > tx) out[qid] = y;
    else if (ty === tx && y.confidentStreak > x.confidentStreak) out[qid] = y;
  }
  return out;
}
```

`lastTouchOf` 取 `[addedAt, lastWrongAt, removedAt]` 中的最大非 null 值。这样：

- 一端手动移出（`removed`，`removedAt` 最新）→ **不会被另一端的旧 active 状态复活**（这点与上游 `applyItemBook` 的 t24 F-01b 安全阀一致）
- 一端连续两次「有把握答对」自动移出（`removedReason:"auto2"`）→ 同样不复活
- 一端新答错（`lastWrongAt` 最新）→ 覆盖旧的 `removed`，题重新入册（符合 `wrongbookApply` 的「removed + 判错 → 重新进入」）

计数字段（`confidentStreak` / `attemptsSinceAdd` / `correctSinceAdd`）跟随胜出的整条条目，不做逐字段 max——逐字段 max 会造出「streak=2 但 attemptsSinceAdd=9」这种状态机无法产生的非法组合，之后 `wrongbookApply` 会基于假状态提前移出错题。

**步骤 C —— 回写客户端**

把合并结果整包回给客户端，客户端 `CQP.setStore(S.store)` 覆盖内存态，并用返回值刷新 `S.store`，让两个设备看到同一份数据。

客户端防抖 250ms 批量提交；`beforeunload` 用 `navigator.sendBeacon('/api/store', ...)` 兜底。

### 4.4 自备题库接入（fixture 适配器，已用原型跑通）

用户已提供两份扁平 schema 题库：`crypto.json`（44 题，38 单选 + 6 多选，8 章）与 `law.json`（32 题，26 单选 + 6 多选，6 章），位置 `D:\JSU\match\ciscn\platform\data\bank\`。单题形状 `{qid,stem,type,options[{key,text}],answer[],explanation,chapter,difficulty}`。

`bk_validateBank`（`src/core/bank.mjs:129`）对题库有硬约束，扁平 schema 不能直接塞进去。适配器 `server/banks.js` 的 `normalizeExternalBank(input, opts)` 按下面 12 步转换（**已用探针脚本对两份真实题库跑通，未报错**）：

1. 章节名 → chapterCode 映射（可配）：`crypto` 全部落 `C05`；`law` 按 密码法→C01、网络安全法→C02、商用密码管理→C03、数据安全法/个人信息保护法→C04、等级保护与标准→C07
2. 按 `(chapterCode, sectionType)` 各自从 1 起编号 `seq`
3. `id = "Q-" + chapterCode + "-" + TYPE_CODES[sectionType] + "-" + seq.padStart(4,"0")`
4. `partCode/partName/chapterName` 从 `CQP.chapterByCode(code)` 取规范值（原章名只能进 `tags`）
5. `single/multiple` 保留 4 个 `{key,text}` 选项；`judge/blank` 置 `[]`
6. `answerStatus:"ok"`、`rawAnswer = answer.join("")`
7. `tags`：章节名 → 词表标签提示表（对称密码→分组密码、非对称密码→公钥密码、哈希与 MAC→杂凑与消息鉴别、签名与 PKI→电子认证与 PKI、国密算法→SM2、商用密码管理→商用密码管理条例、等级保护与标准→标准规范…），为空回退 `CHAPTER_FALLBACK_TAGS[code]`，截断 3 个
8. `sourcePage:1`、`needsReview:false`、`reviewReason:null`、`blankCount`（仅 blank 为 1）
9. `responseMode = CQP.responseModeOf(q)` 强制对齐，否则触发 `E_Q_MODE_MISMATCH`
10. `chapters[]` 按实际计数重算 `chapterTotal` 与 `sections[].count`（必须精确相等，不能照抄原题数）
11. `source` 填 `{fileName:"<slug>.json", pages:1, theoryBlocks:N, printedQuestions:N, excludedCount:0, excludedReason:"外部导入，非原版 PDF"}`

### 6.3 安全

- 密码：`node:crypto` 的 `scrypt(N=16384, r=8, p=1, keylen=64)`，存 `scrypt$N$r$p$saltB64$hashB64`，校验用 `timingSafeEqual`
- 会话：32 字节随机 hex，DB 存 token（不存 hash 的取舍见 §9 A5），默认 7 天；cookie `cqp_sid`，`HttpOnly; SameSite=Lax; Path=/`，`CQP_COOKIE_SECURE=1` 时加 `Secure`
- CSRF：`SameSite=Lax` + 所有写接口校验 `Origin`/`Referer` 与 `Host` 同源；JSON 接口强制 `Content-Type: application/json`
- 限流：按 IP 的登录失败计数（60s 内 >10 次 → 429）+ 按用户名的慢速锁定（连续 5 次失败锁 5 分钟）
- 请求体上限 2MB（题库上传走 8MB 例外）
- 静态文件路径白名单，拒绝 `..`
- 安全响应头：`X-Content-Type-Options: nosniff`、`X-Frame-Options: SAMEORIGIN`、`Referrer-Policy: same-origin`、`Content-Security-Policy: default-src 'self'; style-src 'self' 'unsafe-inline'; script-src 'self' 'unsafe-inline's`（内联脚本必须放行）

> **本机实测的两个坑（都已在真机上解决，脚本要写死）**：
>
> 1. **`apt`/`pkg` 不能用 root 跑** —— `su -c apt ...` 直接返回 `Ability to run this command as root has been disabled permanently for safety purposes.`。必须 `run-as com.termux` 切到 uid `u0_a298` 执行，且要显式给 `PREFIX=/data/data/com.termux/files/usr`（否则 `pkg` 报 `command not found`）。
> 2. **`nodejs-lts` 装完会 `CANNOT LINK EXECUTABLE "node": cannot locate symbol "OSSL_INDICATOR_get_callback"`** —— 因为随包的 `openssl` 是旧的 `1:3.2.1-1`。必须先升级：`apt install -y --only-upgrade -o Dpkg::Options::=--force-confnew openssl`（升到 `1:3.6.5`）再跑 node。**不加 `--force-confnew` 会卡在 `openssl.cnf` 的 conffile 交互问答**（`end of file on stdin at conffile prompt`）。
>

> ```powershell
> adb reverse tcp:18081 tcp:12450          # 手机 18081 → PC 12450 (XSUS 代理)
> # 手机侧：
> export http_proxy=http://127.0.0.1:18081 https_proxy=http://127.0.0.1:18081
> apt update && apt install -y nodejs-lts
> ```
> 这只是安装期的权宜手段。**运行时**手机已能独立出网（实测出口 `112.53.136.22`），frpc 直接跑即可。

**这套方案的三个真实风险（写进 README，不回避）：**

1. **手机侧 NAT 超时比宽带短** —— 空闲 5–15 分钟常见断连。frpc 自带心跳（`heartbeat_interval`）保活；服务端 `GET /api/health` 做成可从外部探活的端点（§9 A13）。
2. **休眠杀进程** —— 即使有 wakelock，部分厂商 ROM 深睡后仍会杀。缓解：插着充电器、把 Termux 加进 `deviceidle` 白名单（`su -c "cmd deviceidle whitelist +com.termux"`）。
3. **流量费** —— 一次 100 题模拟考含成绩页约 0.3 MB；1001 题全刷一遍（含解析）约 3–5 MB。4G 无线上量套餐要给 frpc 设 `bandwidth_limit`，或干脆只在 Wi-Fi 下开。

**与 MiFi 的分工（如果两个都留着）**：手机当主机跑 Node + frpc；MiFi 插上 SIM 后可当手机的 Wi-Fi 热点（现在没卡，这条暂时用不上）。手机若用 Wi-Fi 联网，直接连现有路由器即可。

### 7.3 落地方式（按推荐度排序）

**方案 A（推荐）：旧安卓手机 Termux 当主机 + SakuraFrp 反向隧道**

- 手机内 `node server/index.js` 绑 `127.0.0.1:3010`（收紧暴露面，frpc 同机直连回环）
- 首次自测可临时 `HOST=0.0.0.0`，手机浏览器开 `http://127.0.0.1:3010` 确认后再收紧
- SakuraFrp 建 **TCP 隧道 + 非内地节点**（零域名零备案），本地端口指向 `3010`
- 你已在这台手机跑过 SakuraFrp，**隧道大概已存在** → 只需把隧道里的「本地端口」改成 `3010`
- 接入前的逐项检查与三个真实风险见 §7.2.2

**方案 B（你原本的想法，留作备份）：这台 Windows 当主机 + SakuraFrp**

- 服务绑 `0.0.0.0:3010`，局域网 `http://192.168.0.100:3010`
- `deploy/start.ps1`：`New-NetFirewallRule` 放行 3010（仅 `192.168.0.0/24`）+ 进程守护
- ⚠️ 出网实测（2026-11-26 复测，**结论已修正**）：
  - 直连境外站点确实被卡：`curl https://api.ipify.org` 直连 `HTTP=000`；`api.ipify.org:443`、`1.1.1.1:443` 均 `Test-NetConnection=False`。只有走 `127.0.0.1:12450`（XSUS 代理）才通（出口 `109.110.162.201`）。
  - **但 SakuraFrp 节点是通的**：真实节点域名是 **`cn-hk-N.natfrp.io`**（不是 `.cloud`，`.cloud` 全是 `DNS 名称不存在`）。实测 `cn-hk-1.natfrp.io` → `43.225.47.70`、`cn-hk-2` → `43.225.47.95`、`cn-hk-3` → `64.49.47.22`，**`:7000` 与 `:443` 全部 OPEN**（裸 TCP `Connect` 返回 `True`；用 curl 打 `http://…:7000/` 返回 `HTTP=000`，正符合 frp 不是 HTTP 服务）。
  - 校园网**没有**封 7000 端口；`github.com:22`、`smtp.qq.com:25`、`8.8.8.8:53` 也都 OPEN。
  - → 所以 Windows 跑 frpc **可行**，只是不如手机省电省事。这条降级理由要改成「手机更接近 7×24 常开设备」，不再是「连不上节点」。

**方案 C：一台 Linux VPS 当主机（最省心，但要花钱）**

- 1 核 1 GB 即可（Node 24 + SQLite 常驻约 80 MB），有公网 IP 就不需要 frp
- `deploy/cqp.service`（systemd，`Restart=always`）+ `deploy/nginx.conf.example`（反代 127.0.0.1:3010、`gzip on` 给 `application/json`）

**方案 D：换一块能跑 Linux 的板子当「随身主机」**

如果你确实想要巴掌大的独立主机：GL.iNet GL-MT3000（512 MB）、香橙派 Zero 2W（512 MB）、树莓派 Zero 2 W（512 MB）都能跑 Node 24 + SQLite。它们有 CPU、有内存、有存储，和那台 22 MB 的 MiFi 不是一类东西。

**方案 E：容器化（配合 A/B/C）** — `deploy/DOCKERFILE`（`FROM node:24-alpine`，无 `npm install`，`VOLUME /app/data`）。

**共同点：隧道选型与主机无关**

| 隧道类型 | 节点 | 域名/备案 | 访问形式 | 适用 |
|---|---|---|---|---|
| **TCP** | **必须非内地节点**（穿透 HTTP 应用时内地节点禁止） | 不需要 | `http://frp-xxx.com:12345` | ✅ 零域名零备案，默认选它 |
| HTTP | 内地节点需**备案域名**；非内地不需 | 需要自己的域名 | `http://my.example.com` | 有域名时更漂亮 |
| HTTPS | 同上 | 需要自己的域名 | `https://my.example.com` | 要 HTTPS 时 |

#### 7.3.1 frpc 具体参数（读官方手册后的定稿）

| 项 | 值 / 说明 |
|---|---|
| 版本要求 | **`0.51.0-sakura-14` 及以上**；用 `frpc -V`（大写，`-v` 不是查看版本）确认版本号含 `sakura`，否则失去官方支持与优化 |
| 启动 | `frpc -f <访问密钥>:<隧道ID>`；或环境变量 `NATFRP_TOKEN` + `NATFRP_TARGET` |
| Termux 特例 | 若报 `Segmentation fault`（UPX 与 PRoot/部分内核冲突），在下载地址尾部加 **`_noupx`** 取未压缩版 |
| 带宽限制 | `bandwidth_limit = 2MB`（`0.51.0-sakura-9+`，单位 MiB/KiB），防止手机流量跑飞 |
| 访问认证 | `auth_pass = <密码>`（`auth_mode=online` 默认，也可走面板授权）；公开到外网时建议开，挡掉扫描器 |
| 真实 IP | `auto_https_mode=http`（默认自动探测到 HTTP 服务即为该模式）时 frpc 会追加 `X-Forwarded-For`；但**用 TCP 隧道时 frpc 不做 HTTP 反代，拿不到真实 IP** → 服务端 A11 的信任逻辑要按隧道类型区分 |
| 内网访问 | `local_access = true`（`0.51.0-sakura-9.3+`）可让同一 Wi-Fi 下的设备用 `手机IP:远程端口` 直连，走本地不消耗流量 |
| 掉线行为 | 自动 HTTPS 反代错误默认返回 `502`，可用 `auto_https_error_code` 改；`GET /api/health` 保持轻量便于外部探活（A13） |

> **隧道类型的选择提醒**：走 **TCP 隧道**时 frpc 是纯四层转发，服务端收到的 `remoteAddress` 是 frpc 自己的回环地址，`X-Forwarded-For` **不会**被加（那是 `auto_https_mode=http` 才有的行为）。所以在这种情况下要么接受「所有访问都来自 127.0.0.1」（限流按全局算，A11 的写法要退化为「不按 IP 限流，按用户名限流」），要么改用 **HTTPS 隧道 + 自己的域名** 才能拿到真实 IP。这条必须在 `deploy/frp-tunnel.md` 里写清楚。

## 9. 边界情况与明确取舍

| # | 情况 | 处理 |
|---|---|---|
| A1 | 前端 localStorage 与服务端不一致 | 服务端权威；本地只作离线镜像。任何 `401/403` 不清本地，只提示重新登录 |
| A2 | 两台设备同时在线改同一条记录 | §4.3 合并；`records` 天然幂等，`wrongbook` 按时间戳取胜 |
| A3 | 改昵称后历史记录归属 | **行为变更**：服务器版统一身份，服务端重写该用户全部 `records[].nickname`；但通过 admin 导入进来的「队友」记录保持原名不动（用 `imports[]` 里的来源标记区分） |
| A4 | 服务端 5xx / 断网 | 进入 `S.storageOk=false` 降级：仍可答题（内存态），banner 常驻 + 「重试提交」，恢复后自动 flush |
| A5 | 会话 token 在 DB 里明文 | 可接受（DB 落盘权限受控），换取「管理员可强制下线」。若要加强，改存 `sha256(token)`，代价是无法列出 token 指纹 |
| A6 | 题库版本升级 | `banks.bank_version` 变化时前端提示「题库已更新，旧记录仍保留」；`records` 里带 `bankVersion` 字段，统计时按当前版本过滤（沿用上游 `records.mjs` 的处理） |
| A7 | 题目被删/改但记录还在 | `wrongbookList` 已按 `qById` 过滤掉不存在的题；统计页对孤儿记录只计数不展示题干 |
| A8 | 首个用户就是 admin | 注册时 `SELECT count(*) FROM users` 为 0 → `role='admin'`；并发注册用事务 + `UNIQUE` 兜底 |
| A9 | 时区 | 强制 `TZ=Asia/Shanghai`，启动时检查 `getTimezoneOffset()===-480`，不符则启动日志 warn |
| A10 | 单文件产物的 API 前缀 | 一律相对路径 `/api/...`，支持部署在子路径（`CQP_BASE_PATH=/cqp` 时前端读 `<base href>`） |
| A11 | 反向隧道下的真实 IP | **取决于隧道类型**：<br>· **TCP 隧道**是纯四层转发，frpc 不做 HTTP 反代 → **`X-Forwarded-For` 不会被加**，服务端看到的 `remoteAddress` 全是 `127.0.0.1`。此时按 IP 限流会退化成全局限流，**必须改按用户名限流**（第 5 次失败锁 5 分钟），IP 只写进审计日志。<br>· **HTTP/HTTPS 隧道**（`auto_https_mode=http`，frpc 自动探测到后端是 HTTP 服务即为默认）才会追加 `X-Forwarded-For`，此时限流**必须**读首段，且仅在 `CQP_TRUST_PROXY=1` 时信任，否则伪造头可绕过。参见官方[获取真实 IP](https://doc.natfrp.com/bestpractice/realip.html)。<br>· 实现要求：`server/http.js` 的 `clientIp(req)` 返回 `{ip, trustProxy}`，限流器按「有可信代理 → IP，否则 → 用户名」双通道。 |
| A12 | 反向隧道下的 Cookie / HTTPS | TCP 隧道外层是 `http://host:port`，浏览器的 `Secure` cookie 会失效。`CQP_COOKIE_SECURE` 默认 **0**（走 TCP 隧道），只有上了 HTTPS 隧道或自己加了 TLS 反代才置 1 |
| A13 | 反向隧道断线 | frpc 掉线时用户侧直接 502，服务端无感。客户端已有 A4 的降级路径；服务端不需要额外处理，但 `GET /api/health` 要能返回 `{ok:true,rev,uptime}` 便于 frp 侧或外部探活 |
| A14 | 隧道免费额度 | SakuraFrp 免费用户的隧道数/带宽/流量有上限，**登录页需要显示「当前为共享节点」提示**；模拟考一次 100 题 + 成绩页共约 300 KB 流量，需在 README 里给出「一次完整模拟考约 0.3 MB」的估算，避免流量用尽才发现 |
